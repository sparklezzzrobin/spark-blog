这篇文章是 spark.geo 的建造日志——它同时回答三个问题：这个站是怎么来的、它现在长什么样、以后要怎么用和怎么长。

## 0x01 为什么自己写一个博客

需求很朴素：一个能长期用的个人站，发学习笔记、记录 GIS / 遥感实践、展示项目、当作品集入口。现成平台（知乎、博客园、CSDN）能满足前两条，但满足不了两个关键诉求：

- **内容归自己**：文章是 md 文件躺在自己的 Git 仓库里，不依附于任何平台的生命周期；
- **把工程链路完整练一遍**：产品设计 → 技术选型 → 前端开发 → Git 工作流 → CI/CD 部署，这个项目本身就是学习项目。

所以定位从一开始就不是"搭个博客"，而是"**做一个以 GIS × 遥感 × 数据 × 编程为标签的技术实践博客 + 轻量作品集**"——文章是过程，项目是结果，两者互链。

## 0x02 设计先行，代码后行

动手写代码之前，先花了一整个阶段做产品与设计规划，产出了设计规范草案，核心决策包括：

- **信息架构只留 5 个页面**：首页、文章列表、文章详情、项目、关于。友链、归档、留言板这些"看起来该有"的页面全部砍掉；
- **视觉基调**："克制的技术感"——大量留白、中性灰底、深青主色（取自水体/植被遥感色系 `#0D7377`）、暖沙点缀色（`#C2A878`，等高线的颜色）；
- **GIS 元素是调味料不是主菜**：等高线纹理退在 Hero 背景、页脚放一行经纬度坐标、日期/标签/坐标全部用等宽字体——技术感由细节传达，不靠大图堆砌；
- **明暗双模式**第一版就做，动画只保留淡入和 hover 微反馈；
- **不做的东西**和要做的同样明确：无评论、无搜索、无后台、无数据库、文章不强制配封面图。

事后看，"先定规范再写代码"省了大量返工——后面所有页面和组件都是照着规范长出来的。

## 0x03 技术选型：为什么是 Astro

对比过四个方案（Astro / Next.js / Hugo / Hexo），选 Astro 的理由：

| 维度 | 结论 |
| --- | --- |
| 内容模型 | 文章就是 md 文件 + frontmatter，天生为内容站点设计 |
| 性能 | 默认零 JS，静态生成，加载极快 |
| 学习价值 | 组件化、npm 工程、Git、部署流水线，技能全部可迁移 |
| 复杂度 | 比 Next.js 轻得多，V1 不需要 SSR 的心智负担 |

配套：Tailwind v4 做样式（色彩令牌直接映射设计规范）、Shiki 代码高亮（明暗双主题）、KaTeX 数学公式、`@astrojs/rss` 订阅、sitemap 自动生成。全部直接依赖 7 个，刻意不引 UI 组件库——卡片、导航这些自己写，既是学习也是规范的直接实现。

**无数据库、无后台**是深思熟虑的决定：周更频率的内容用 Git 当数据库绰绰有余，"编辑器 + commit + 自动部署"就是最好的 CMS，还免掉了备份、安全补丁和认证的维护成本。

## 0x04 V1.0 现状清单

截至本文发布，站点已上线运行于 Vercel（GitHub push 自动部署），功能清单：

**文章模块**

- Markdown + frontmatter，类型校验（写错字段构建期报错）
- 标签筛选（受控词表 ≤ 15 个标签），支持 `/posts/?tag=xxx` 直达
- 代码高亮（明暗双主题）、数学公式、表格、中文排版优化
- 文章目录 TOC：桌面端右侧常驻 + 滚动高亮当前章节，移动端文首折叠
- 上一篇 / 下一篇导航、系列文章标记

**项目模块**

- 与文章同构的 md 内容模型（frontmatter 驱动卡片，正文渲染详情页）
- 详情页含状态徽章、技术栈、访问/源码按钮、上一个/下一个
- **相关文章自动关联**：项目 tags 与文章 tags 取交集，"项目是结果、文章是过程"自动互链

**站点级**

- 明暗模式（跟随系统 + 手动切换，无闪白）
- 响应式（桌面 / 平板 / 手机）
- RSS 订阅、sitemap、Open Graph 基础 SEO
- 等高线风格 favicon

## 0x05 踩过的坑（按时间序）

这部分是写给未来的自己和搜索引擎的。

**1. npm 拦截 esbuild 安装脚本。** 初始化时 `npm install` 的 allow-scripts 机制拦掉了 esbuild 的 postinstall，Astro 起不来。解决：`npm approve-scripts esbuild`。新版本 npm 的安全机制，报错信息会明确提示。

**2. Astro 7 默认 Markdown 处理器不支持数学公式。** Astro 7 换用了新的 Sätteri 处理器（Rust 编写，很快），但插件生态还是 remark/rehype 的。装了 `remark-math + rehype-katex` 后构建报错，提示需要 `@astrojs/markdown-remark`——切回 Unified 处理器后解决。教训：**新框架大版本升级后，生态插件的兼容性要先查文档**。

**3. 类型校验拦截空 URL 字段。** 项目数据里写了空的 `repo: ""`，不符合 schema 的 URL 校验，构建直接失败。这不是 bug 是特性——frontmatter 写错在构建期就暴露，不会带病上线。

**4. 忘写 pubDate 导致文章"消失"。** 新文章写完 frontmatter 漏了 `pubDate`（必填字段），本地页面上不显示。原因是校验失败的文章不进集合。**记牢：title 和 pubDate 是仅有的两个必填字段。**

**5. 开发服务器进程残留。** 改了文件但页面不更新，排查发现之前的 dev 进程没死干净还占着端口。Astro 7 有进程注册（`astro dev stop`），实在不行 `taskkill` 端口进程再起。通用心法：**先 Ctrl+Shift+R 硬刷新，再重启 dev server，能解决九成"玄学问题"**。

**6. 项目文件夹被占用无法移动。** 把项目从工具默认目录迁到桌面时 `mv` 报 "Device or resource busy"——没有残留进程，是编辑器/资源管理器开着那个文件夹占住了工作目录。解决：**目录被占只影响删除重命名，不影响读取**，完整复制到新位置 → 验证构建 → 删除旧目录。Git 仓库整体搬迁，远程和 Vercel 完全无感。

## 0x06 日常使用手册

**写文章**：在 `src/content/posts/` 新建 `YYYY-MM-DD-slug.md`：

```yaml
---
title: 标题            # 必填
pubDate: 2026-08-16    # 必填
description: 一句话摘要  # 建议（列表页和 RSS 显示）
tags: [gis, python]    # 选填
series: 算法学习笔记    # 选填
updated: 2026-08-20    # 选填
---
正文（支持代码/公式/表格/图片）
```

**加项目**：在 `src/content/projects/` 新建 md，frontmatter 含 name / description / tech / status / year / tags，正文自由发挥，详情页自动生成。

**三层心智模型**（Git 工作流的核心认知）：

```
md 文件（磁盘） ← npm run dev 直接读，本地预览
git commit      ← 本地存档，永不上线
git push        ← 唯一的发布动作，触发 Vercel 自动部署
```

本地预览不需要任何 git 操作；想攒几篇一起发，就只 commit 不 push，发布时机完全自己掌控。

## 0x07 后续路线

## 0x08 小结

一个周末量级的投入，换来一条完整的"写作 → commit → push → 自动上线"流水线，以及一份可以指着说"这是我做的"的作品。接下来最重要的事不是加功能，而是**写**——让这个站先跑起来、长起来。
